# Build ALRO's memory as a promise ledger

ALRO should not adopt a graph database or a GraphRAG framework in Phase 1. It should build a **temporal knowledge graph inside Neon Postgres**: an append-only log of every message, typed tables for people, companies, deals and facts with "valid from / valid to" dates (the design used by Zep's open-source Graphiti engine), and a first-class `commitments` table that changes status only when there is evidence. An agent queries all of it through hybrid keyword and vector search. Three findings drive this. First, Graphiti is the only mature open-source engine built for facts that change over time ("promised the deck by Friday" becomes "delivered Thursday"), but it is Python-only, needs Neo4j, FalkorDB or Neptune, and has no Postgres backend ([Graphiti](https://github.com/getzep/graphiti)). Second, the independent evidence does not show graph memory beating well-tuned retrieval for the single-hop, time-filtered questions ALRO users mostly ask. In Mem0's own paper, sending the full conversation beat every memory system, and the graph variant added only about 1.6 points ([arXiv 2504.19413](https://arxiv.org/html/2504.19413)). Third, ALRO needs per-user permissions (a WhatsApp DM is not company knowledge), and Postgres row-level security enforces those far better than a second datastore would. The two 360labs reference products describe exactly ALRO's feature set: a "semantic memory graph" of promises and deadlines, plus a "who am I waiting on" view. They publish no technical detail, though, and come from a services agency, so they are a UX checklist rather than a technology benchmark ([OmniAgent](https://www.360labs.ai/products/omniagent)). The gap no one fills is a commitment-native, evidence-linked memory across WhatsApp, Zoho, CRM, email and meetings at SMB prices. ALRO's moat is closure detection (knowing a promise was kept), not the choice of database.

## RAG, graph and temporal memory in plain language

**Plain RAG** ("retrieval-augmented generation") works like a fast librarian. When you ask a question, it finds the passages from your Slack, email and transcripts that read most like the question, and the AI answers from those. It is cheap and good at "what did Ravi say about pricing last week?" It has no notion of *who* Ravi is, which deal he belongs to, or whether a statement from March was overturned in May. Every question starts from scratch.

**Graph memory** adds a map. As messages arrive, an AI reads them and writes down the things in them (people, companies, deals, projects) and the lines between them ("Priya owns the Acme deal", "Acme is blocked on the SSO feature"). The agent can then follow lines. Text search alone handles "which customers did Priya's team promise features to that depend on the Q3 release?" badly. The cost is that an AI has to read and interpret every message, which takes money and time and introduces mistakes.

**Temporal (time-aware) memory** puts dates on every line in the map. When a new message contradicts an old fact, the old one is not erased. It is marked "true from 3 March until 9 May". You can then ask what is true now, what was true at the board meeting, or which promises are still open. That is exactly the shape of ALRO's commitment tracker: a promise is a fact with an owner, a recipient, a due date and a status, and it stays open until evidence closes it.

The rest of this report argues that ALRO needs the third idea, but can build it on the Postgres database it has already chosen, without a separate graph database.

## 360labs sells the same promise, without showing the machinery

OmniAgent is pitched as a self-hosted, privacy-first assistant that runs 24/7 on the user's own server. It connects to WhatsApp, Telegram, Gmail, Slack, Discord "+15 more" and keeps conversations, sentiment, **promises and deadlines in a "semantic memory graph"**. Its dashboard suggests prompts such as today's commitments, **overdue items** and **"who am I waiting on"**. It has a "Brain" graph visualisation, and it **requires confirmation before every action** (sending email, booking meetings, replying) ([OmniAgent](https://www.360labs.ai/products/omniagent)). Enterprise Brain is the team version: a self-hosted knowledge layer that builds graphs with "multi-hop relationships among people, decisions, deadlines, metrics, processes", where "every answer traces back to a source in your own data" ([Enterprise Brain](https://www.360labs.ai/products/enterprise-brain)). Neither page names models, connectors in depth, a permission model, benchmarks or prices.

The company behind them, Lightyear 360 Labs Pvt Ltd, describes itself as an Indian "AI-native Product Studio & AI Engineering Lab". Its FAQ prices *services*: about $10k for agents and automations and $100k–500k for enterprise platforms ([360labs](https://www.360labs.ai/)). A web search found no independent coverage of 360labs.ai, only an unrelated VR studio with a similar name ([Crunchbase](https://crunchbase.com/organization/360-labs)). The honest reading is that 360labs validates ALRO's feature list and UX vocabulary (graph view, overdue items, "waiting on", human-in-the-loop actions, source citations). It is also the closest positioning analogue, being India-based and WhatsApp-first. It does not prove that a particular architecture works. ALRO can differentiate on cloud onboarding instead of hardware and self-hosting, on Zoho and CRM depth, and on demonstrable closure-detection accuracy.

## Graphiti leads time-aware memory, but nothing runs natively on Neon and TypeScript

The open-source field splits into three families. **Temporal graph engines** (Graphiti/Zep) model facts that change. **GraphRAG-style indexers** (Microsoft GraphRAG, LightRAG, HippoRAG, nano-graphrag, fast-graphrag, KAG) summarise a mostly static document collection. **Agent-memory layers** (Mem0, supermemory, Letta, Cognee, LangMem) remember things about a user for a chatbot. Only the first family matches ALRO's core job.

**Graphiti** (32.3k stars, Apache-2.0, release v0.31.2 on 20 Oct 2026) stores raw messages as "episodes", extracts entities and facts from them, and gives every fact validity windows. Changed facts are "invalidated — not deleted", so you can "query what's true now, or what was true at any point in time". Retrieval combines embeddings, BM25 keyword search and graph traversal ([Graphiti](https://github.com/getzep/graphiti)). The Zep paper lays out the mechanics ALRO can copy. Each fact carries two timelines: when it was true (`t_valid`/`t_invalid`) and when the system learned it (`t′created`/`t′expired`). An LLM compares each new fact against related existing ones and closes the old fact's validity window on contradiction. Entity resolution uses name-embedding similarity plus full-text search, followed by an LLM duplicate check. Graph writes use fixed queries rather than LLM-written ones. On LongMemEval with GPT-4o it reported **71.2% versus 60.2% for full context, at 2.58 s versus 28.9 s latency and about 1.6k versus 115k context tokens** ([arXiv 2501.13956](https://arxiv.org/html/2501.13956v1)). The limits matter for ALRO. Graphiti supports Neo4j, FalkorDB, Neptune and a now-deprecated Kuzu, **but not Postgres**. It has no official TypeScript port. Its MCP server "do[es] not authenticate callers", and its `group_id` namespace is a partition, not a per-user permission system ([Graphiti](https://github.com/getzep/graphiti), [Zep namespacing](https://help.getzep.com/graphiti/graphiti/graph-namespacing)). The self-hosted Zep Community Edition is deprecated. The managed Zep Cloud, which does ship a TypeScript SDK and Vercel AI SDK integration, now runs on Zep's own graph engine ([getzep/zep](https://github.com/getzep/zep)).

Each of the other candidates fails on at least one of ALRO's requirements.

| Project | What it is good at | Why it falls short for ALRO Phase 1 |
|---|---|---|
| [Microsoft GraphRAG](https://github.com/microsoft/graphrag) (36.5k, MIT) | "Global" questions over a document corpus via community summaries | Batch pipeline, no notion of time. Graph extraction is ~75% of indexing cost ([docs](https://microsoft.github.io/graphrag/index/methods/)). Its Postgres graph store is believed to rely on Apache AGE, which Neon does not offer ([Neon extensions](https://neon.com/docs/extensions/pg-extensions)) |
| [Mem0](https://github.com/mem0ai/mem0) (67.9k, Apache-2.0) | Native TypeScript SDK, pgvector support, Vercel AI SDK provider | Personal or chatbot scope (user/session/agent). | [Letta](https://github.com/letta-ai/letta) (25.3k) | Agent self-edits memory blocks; background "sleep-time" consolidation | Agent-centric memory, not an organisational knowledge graph |

| [R2R](https://github.com/SciPhi-AI/R2R) | Was the closest "Postgres-native GraphRAG with ACLs" | Last release June 2025, last push Nov 2025: effectively stalled |

Two warnings. LangChain's `langchain-experimental` repo, which held the `LLMGraphTransformer`, is now archived ([repo](https://github.com/langchain-ai/langchain-experimental)). Separately, a single source reports that four MemTensor packages, including npm `@memtensor/memos-cloud-openclaw-plugin` and PyPI `MemoryOS`, were published with a Go implant on 23 Sep 2026 ([OrcaRouter](https://www.orcarouter.ai/blog/2026-09-23-memtensor-sckit-supply-chain)). ALRO should not install MemOS-family packages without checking that report.

On the open-source "company brain" side, two projects deserve study rather than adoption. **Onyx** (33k stars) has the most mature connectors (Slack, Gmail, Salesforce, Google Drive, SharePoint and others) and per-document ACLs synced from the source system. However, permission sync sits in its Enterprise Edition licence, and the code is Python ([Onyx permissioning](https://docs.onyx.app/enterprise_edition/permissioning)). **supermemory's company-brain** (Apache-2.0, TypeScript) is a discontinued Slack product that was open-sourced. Its permission rule is worth copying exactly: public channels share memory, private channels add that channel's memory, and DMs add personal memory. Reads run with the asker's own access, and borrowing a teammate's tool connection needs their approval ([company-brain](https://github.com/supermemoryai/company-brain)). Neither project treats commitments as a data type, and no open-source project reviewed has WhatsApp or Zoho connectors.

## Benchmarks do not crown graph memory, and extraction is the bill

The headline memory leaderboards are mostly vendor self-reports and should not drive ALRO's choice. In Mem0's own LoCoMo evaluation, **full context scored 72.9**, against 68.4 for the graph variant Mem0g, 66.9 for plain Mem0, 66.0 for Zep and 61.0 for the best plain RAG setup. The graph gain was small, and it doubled the memory footprint, from ~7k to ~14k tokens per conversation ([arXiv 2504.19413](https://arxiv.org/html/2504.19413)). Zep originally claimed 84% on the same benchmark, then corrected it to 75.1% after Mem0's CTO showed adversarial questions had been miscounted. The two companies still dispute each other's methodology ([zep-papers#5](https://github.com/getzep/zep-papers/issues/5)). Letta then scored **74.0% with GPT-4o-mini using nothing but file search and an agent loop**, beating both ([Letta](https://www.letta.com/blog/benchmarking-ai-agent-memory)). On LongMemEval, the top GPT-4o system is Mastra's Observational Memory at 84.2%, which is a compressed text log rather than a graph. Swapping only the reader model moved Mastra's score by about 10 points, so numbers across vendors are not comparable ([Mastra](https://mastra.ai/blog/observational-memory)). Mem0's self-reported 94.4% on LongMemEval sits alongside an independent figure of 49.0% ([Atlan](https://atlan.com/know/best-ai-agent-memory-frameworks-2026/)).

Academic comparisons point to the same split. A systematic study found plain RAG does well on single-hop factual questions and graph RAG helps on multi-hop ones, while GraphRAG's "global" mode generally underperformed RAG ([arXiv 2502.11371](https://arxiv.org/abs/2502.11371)). The ICLR 2026 GraphRAG-Bench paper starts from reports that "GraphRAG frequently underperforms vanilla RAG on many real-world tasks". It finds graphs help evidence recall on complex reasoning and summarisation, while RAG keeps higher context relevance ([arXiv 2506.05690](https://arxiv.org/abs/2506.05690)). ALRO's bread-and-butter questions ("what did we promise Acme?", "is the invoice follow-up done?") are single-hop and time-filtered. Graph structure pays off on the rarer multi-hop questions and on "what are the recurring complaints across accounts?" style summaries. No benchmark tests workplace data (email, Slack, CRM) or commitment tracking. LongMemEval-V2's "experienced colleague" framing is the closest ([arXiv 2605.12493](https://arxiv.org/pdf/2605.12493)).

Extraction cost is the main weakness of graph memory. Graphiti makes several serial LLM calls for each message ingested. One user measured about **$0.80 for 40 short chats (~$0.018 each)** on default OpenAI models. The maintainer says token use has since dropped and a cheap classifier model was added, but publishes no new figure ([graphiti#467](https://github.com/getzep/graphiti/issues/467)). On a rate-limited endpoint with concurrency of 1, a single sentence took about 626 seconds ([graphiti#1516](https://github.com/getzep/graphiti/issues/1516)). Open issues also report episodes silently dropped while the call returned success ([graphiti#1707](https://github.com/getzep/graphiti/issues/1707)). LightRAG-style indexing needs roughly 10k tokens per document ([arXiv 2604.16350](https://arxiv.org/pdf/2604.16350)). A rough extrapolation, not a measurement: an SMB generating 5,000 messages a day, each run through Graphiti-style extraction with GPT-4o-class models, would cost on the order of $25–100 a day, which is untenable at SMB price points. Smaller models, batching whole threads and only running extraction on messages that matter bring this down sharply. Microsoft's LazyGraphRAG shows the same lesson from the other side. It replaces up-front LLM summarisation with cheap noun-phrase extraction and claims indexing cost equal to vector RAG, **0.1% of full GraphRAG** ([MSR](https://www.microsoft.com/en-us/research/blog/lazygraphrag-setting-a-new-standard-for-quality-and-cost/)).

Commitment extraction carries its own accuracy warning. Microsoft Research showed email commitment classifiers degrade when moved to a new domain ([WSDM 2019](https://www.microsoft.com/en-us/research/wp-content/uploads/2019/01/AzarbonyadWSDM2019.pdf)). Microsoft shipped commitment detection in Viva Briefing and then, in February 2024, removed commitments and requests drawn from email and chat from Viva Insights suggestions ([MC713042](https://mc.merill.net/message/MC713042/v/2024-02-06T00-10-10-407Z)). The likeliest reading is that precision at scale was hard to achieve. Every startup commitment tracker reviewed (Claryti, Promiso, Lodestar, Rapto) publishes only self-reported outcomes ([Claryti](https://www.claryti.ai/features/commitment-tracking), [Rapto](https://www.rapto.cloud/)). ALRO should assume it will need user confirmation, confidence scores and its own evaluation set from day one.

## Postgres can carry the graph, and it enforces privacy better

For Phase 1, a graph is just two tables: entities, and edges between them. Neon offers pgvector (0.8.0, or 0.8.6 on PG18), pg_trgm and ltree. It **does not offer Apache AGE (Cypher on Postgres), pgvectorscale, or pg_search BM25** ([Neon extensions](https://neon.com/docs/extensions/pg-extensions)). So "graph in Postgres" on Neon means an entities table and an edges table, indexed adjacency, and recursive queries or two or three chained joins. That is enough for the 1–3 hop lookups a company brain needs. On pgsql-hackers, a naive recursive query ran in 299 ms against 528 ms for Neo4j even after a Neo4j index was added ([PostgreSQL list](https://postgresql.org/message-id/0e98dbc4-4116-4e15-bf72-3a7d4ab0d27d%40app.fastmail.com)). Recursive queries do break down on deep or unbounded traversals: one extension author reports 47 s versus 227 ms on a 335k-node tree ([pg_igraph](https://pgxn.org/dist/pg_igraph/)). They also struggle with whole-graph algorithms such as community detection. ALRO should therefore cap query depth, add cycle guards, and push any graph analytics to background jobs.

Two pgvector details will bite at scale. Filtered vector search silently loses recall unless pgvector 0.8's iterative index scans are switched on. With a filter matching 10% of rows and default settings, a request for 10 results returns about 4 ([Render](https://render.com/articles/multi-tenant-rag-postgresql-pgvector)). The HNSW index also needs to fit in RAM, and 1M × 1536-dimension vectors already did not fit in one test ([thebuild.com](https://thebuild.com/blog/on-pgvectorscale-and-hybrid-search-without-an-elasticsearch-sidecar/)). Using 512–1024-dimension embeddings stored as `halfvec`, and partitioning by tenant, keeps Neon viable well into millions of messages.

The decisive argument is permissions. ALRO's privacy boundary is per user, not per company: a WhatsApp DM, a private Slack channel and a personal inbox each have their own audience. Postgres row-level security can enforce "show this fact only if the asker can see at least one of the messages it came from" inside the database, for vector search, keyword search and graph traversal alike ([Render](https://render.com/articles/multi-tenant-rag-postgresql-pgvector)). Graph databases mostly isolate whole databases or graphs. Neo4j offers multiple databases per instance only on Business Critical ([Neo4j pricing](https://neo4j.com/pricing/)), and FalkorDB offers a graph per tenant. Per-user filtering inside a tenant has to be written into every query, and a traversal can leak through a node the user should not see. Cost points the same way. Neon storage is about $0.35/GB-month, with compute at $0.106–0.222 per CU-hour ([Sacra](https://sacra.com/research/neon), secondary). Neo4j Aura runs about **$65/GB-month (Professional) or $146/GB-month (Business Critical)**, so a modest 8–16 GB graph adds roughly $500–2,300 a month ([Neo4j pricing](https://neo4j.com/pricing/)). If ALRO later needs a dedicated engine, the realistic choices are FalkorDB (SSPL licence, official TypeScript client, Graphiti-supported, vendor-claimed 10,000+ graphs per instance) or Neo4j Aura ([FalkorDB](https://github.com/FalkorDB/FalkorDB)). Kuzu was archived in October 2025 after Apple acquired its developer ([OneUptime](https://oneuptime.com/blog/post/2026-08-12-kuzu-archived-pin-0-11-3-fork-or-migrate/view)).

## Big vendors say "graph" but none of them track promises

The commercial "graph" products are relevance and permission graphs, not graphs of commitments. Glean's Knowledge Graph links content, people and activity signals across 100+ connectors with permissions mirrored from each source ([Glean docs](https://docs.glean.com/security/knowledge-graph)). It is priced for enterprises: a Vendr median contract of about $99k/year, and a reported minimum of around 100 seats ([insearch](https://insearch.ai/glean-pricing), [Macha](https://www.getmacha.com/blog/glean-ai-complete-guide)). Atlassian's Teamwork Graph, Notion AI enterprise search (about $20/member/month in the Business tier, keeping each connector's permissions) and Dust (about $29–30/user/month, admin-defined Spaces rather than per-user ACL mirroring) are similar ([gend.co](https://www.gend.co/blog/notion-pricing), [Dust](https://dust.tt/landing/glean)). Day.ai's CRM "context graph", which stores decision traces such as why deals closed, is the nearest graph-native competitor. It raised a $20M Series A led by Sequoia in February 2026 ([Ramp](https://ramp.com/leading-indicators/the-ai-digest-february-3-2026), [Dealroom](https://dealroom.co/companies/day-ai/)).

Promise tracking itself is crowded, but the players are small. Claryti, Promiso, Ally, Lodestar and Rapto all extract commitments, mostly from meetings and email ([Promiso](https://promiso.ai/), [Lodestar](https://www.getlodestar.ai/blog/daily-execution/follow-through/)). Notetakers such as Granola ($14/user/month Business) and Fireflies ($10–39/seat) draft action items ([Granola](https://www.granola.ai/blog/meeting-note-tool-pricing-granola-vs-fireflies-fathom-otter), [Fireflies](https://fireflies.ai/blog/granola-vs-fireflies)). The biggest threat is Microsoft. Copilot in Outlook is rolling out "surfacing follow-ups across email and meetings" and "spotting upcoming commitments" ([Microsoft](https://learn.microsoft.com/en-us/microsoft-365/copilot/release-notes)), and Planner Agent turns meeting follow-ups into tasks ([Tech Community](https://techcommunity.microsoft.com/blog/plannerblog/planner-agent-brings-work-management-directly-into-microsoft-365-copilot/4511720)). That leaves companies that run mainly on Microsoft 365 contested. Companies on Google, WhatsApp, Zoho or a mix are underserved.

## Recommended Phase 1 architecture: five layers in one Postgres

ALRO should build a relational re-implementation of Graphiti's ideas in TypeScript on Neon (Apache-2.0 permits copying the design). It should treat commitments as the product and the graph as plumbing. The table below lists each layer. Every part runs inside the existing Next.js/Vercel and Neon stack, with ingestion and extraction as background jobs.

| Layer | What it stores / does | Key design rules |
|---|---|---|
| 1. Evidence log | Every Slack, Teams, Gmail, WhatsApp and CRM event and transcript segment, kept immutable in `messages`, plus chunks with pgvector (`halfvec`, ≤1024 dims) and `tsvector` | Never edit or delete derived facts in place. Each row carries tenant, source, thread, participants, timestamp and **ACL principals** (who could see it in the source) |
| 2. Entity graph | `entities` (person, company, deal, project), `entity_mentions`, and `edges` with `valid_from`, `valid_to`, `recorded_at`, `expired_at` and `source_message_ids` | Bi-temporal columns as in the Zep paper. Contradictions close the old edge's validity window instead of deleting it. Entity resolution by name-embedding plus trigram match, then an LLM check |
| 3. Commitment ledger | `commitments` (owner, counterparty, what, due date, status, confidence, evidence ids) and `commitment_events` (status changes) | Extract per **thread window**, not per sentence. Status changes only on evidence (a reply saying "sent", a CRM stage change, a calendar event). Users confirm or dismiss low-confidence items, and every decision becomes eval data |
| 4. Agent tools | AI SDK tools: hybrid search (tsvector + pgvector fused with RRF, then rerank), open thread, list open or overdue commitments, entity neighbourhood (1–3 hop query with a depth cap), time filters | An agent loop rather than a single retrieval step. Every answer cites source messages. Actions ("send reminder") need user confirmation, as in OmniAgent and company-brain |
| 5. Consolidation | Nightly rollups per account, project and week; re-checks of overdue commitments; reminder triggers | Replaces GraphRAG-style community summaries for "big picture" questions at a fraction of the cost |

**Cost control.** Run a cheap classifier on each new message to decide whether it contains a commitment, a decision or a change of fact. Only those messages, batched by thread, go to full extraction with a small model. Everything else stays searchable in layer 1. This targets the per-message LLM bill that makes Graphiti expensive.

**Privacy.** Enforce row-level security keyed on the asker's principals (user id, channel memberships, mailbox), with a GIN index. A derived fact or commitment is visible only if the user can see at least one supporting source message. Adopt company-brain's scoping: public channel memory is shared, private channel memory is channel-only, and DM, WhatsApp and personal email memory is personal. Personal channels must never leak into "company" answers.

**Measurement.** Before tuning anything, build a 100–200 question evaluation from consented pilot data. Include commitment open/closed questions and "what changed since" questions. Vendor benchmarks will not tell ALRO what works on its own users' data.

**When to revisit.** Most of this design can be kept on Postgres permanently, but four signals would justify a change. If real usage shows multi-hop questions dominating, if graph analytics are needed, or if traversals deeper than about four hops become common, export the entities and edges into Graphiti on FalkorDB or Neo4j. Because the schema mirrors Graphiti's from day one, that move is an ETL job rather than a rewrite. If vector volume outgrows Neon compute, add a dedicated vector store or a host with pgvectorscale. If speed to a demo matters more than control, Zep Cloud's TypeScript SDK is the fastest way to get temporal graph memory. ALRO would then be handing customer data to a vendor, mapping per-user permissions onto Zep's namespaces itself, and paying Zep's credit-based pricing (sources conflict: about $125–375/month on the Flex tiers ([Atlan](https://atlan.com/know/best-ai-agent-memory-frameworks-2026/))). That fits an internal prototype, not the product.

## Conclusion

In 2026, the useful question is not "RAG or graph". It is which facts deserve to be structured, and who proves when they stop being true. The memory vendors' own evidence answers both. Mem0 abandoned in-place LLM edits for append-only memory ([Mem0](https://github.com/mem0ai/mem0)), Graphiti invalidates rather than deletes, and Microsoft pulled back from email commitment detection. Together these show that the hard, valuable part is evidence-linked change over time, not the graph store. That also makes ALRO's moat measurable: precision on extracted promises, recall on closure detection, and per-user privacy that a CFO and an employee's WhatsApp can both trust. None of the reviewed competitors publishes any of these numbers.

The graph is not the main risk. The weakest assumptions are that LLM extraction can find promises accurately across WhatsApp Hinglish, Zoho notes and meeting transcripts, and that closure can be detected automatically. No public data shows this, and Microsoft's retreat suggests it is hard. ALRO's first engineering milestone should be a commitment-extraction evaluation on real pilot data, run before any connector beyond Slack and Gmail is built. A Postgres-first design keeps the infrastructure bill low enough to run that experiment cheaply, and leaves Graphiti or FalkorDB available later if the data shows they are needed.
